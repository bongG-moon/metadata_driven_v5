학습용 구현 안내서 · Flow 07-1 / 07-2

여러 원천 데이터를 쓰는 Report를
안전하게 만들고 후속 질문까지 받는 방법

이 문서는 “중간 소스가 3개든 10개든, 왜 Flow 07-2에는 최종 결과 View만 넘기는가?”를 실제 구현 예시와 함께 설명합니다. 핵심은 복잡한 계산은 Report Recipe에서 끝내고, 후속 질문은 저장된 완성 View 안에서만 처리하는 것입니다.

한 문장으로 이해하기

Report Recipe는 “요리사”, Flow 07-2는 “완성된 메뉴에서 찾고·정렬하고·골라 주는 직원”입니다. 직원에게 주방의 모든 재료와 조리법을 맡기지 않습니다.

현재 구현 기준

07은 기존 직접 Report, 07-1은 View를 저장하는 향상된 Report, 07-2는 저장된 View의 후속 질문 전용 Flow입니다.

빠른 이동 전체 구조 3개 소스 예시 Recipe 코드 00E 자동 처리 10개 소스 예시 후속 질문 HTML Report 작성 체크리스트

1. 먼저 전체 구조를 한 번에 보기

“중간 소스”는 Report를 만들기 위한 재료입니다. 반면 “공개 View”는 이미 계산이 끝난 결과물입니다. Flow 07-2는 전자에 접근하지 않고 후자만 읽습니다.

2. 예시 ① — 중간 소스가 3개인 “생산부족·장비위험 제품” Report

아래 Report는 생산부족 제품 중에서 장비 위험까지 있는 제품을 찾는다고 가정합니다. 사용자는 나중에 “생산실적달성율이 낮은 순으로 5개 보여줘”라고 물을 수 있습니다.

production_cases

제품·공정별 생산량, 계획량, 생산 판정

target_plan

제품별 목표량 또는 기준 계획

equipment_assign

제품별 필요 장비 수, 교체 판단

↓

Report Recipe가 하는 계산

  1. 입력 검증필수 소스가 모두 있고, 조인에 필요한 제품 키와 계산 컬럼이 존재하는지 확인합니다.
  2. 제품 단위로 조인·집계공정별 생산 Case를 제품별로 합산하고, 장비 판단을 붙입니다.
  3. 비율은 다시 계산생산실적달성율 = 생산량 합계 ÷ 계획량 합계 × 100으로 계산합니다. 공정별 비율을 단순 평균하지 않습니다.
  4. 공개할 View 완성후속 질문에 필요한 행과 컬럼만 가진 “생산부족·장비위험 제품” View를 만듭니다.

최종적으로 공개되는 View의 모습

L-256K9B72.4장비필요3
SP 24G GDDR781.7교체필요1
HBM-TEST88.1정상0

이 표가 Flow 07-2에 저장되어 후속 질문의 대상이 됩니다. 세 개의 원천 테이블은 직접 공개하지 않습니다.

3. Recipe 코드는 어디까지 작성하면 될까?

Report 작성자가 직접 만들어야 하는 것은 업무 계산과 완성된 View의 행입니다. report.query_source.v1 같은 내부 실행 계약을 직접 조립할 필요는 없습니다.

아래 코드는 이해를 위한 작은 예시입니다. 실제 프로젝트에서는 이 함수를 Langflow Custom Component의 핵심 함수로 넣고, 각 원천 Data를 입력으로 연결하면 됩니다. 데이터 조회 자체는 Recipe 앞단의 기존 노드가 담당합니다.

3-1. 먼저 업무 계산을 하는 Python

# 예시: 세 원천을 받아 “제품 위험” 완성 View를 만든다.
def build_product_risk_rows(production_cases, target_plan, equipment_assign):
    # 1) 필요한 컬럼을 먼저 확인한다. 없으면 추측해서 진행하지 않는다.
    required = {
        "production_cases": {"제품", "생산량", "계획량"},
        "equipment_assign": {"제품", "장비교체판단", "필요장비대수"},
    }
    assert_required_columns(production_cases, required["production_cases"])
    assert_required_columns(equipment_assign, required["equipment_assign"])

    # 2) 공정별 Case를 제품별로 합산한다.
    totals = sum_by_product(production_cases,
                            product_column="제품",
                            sum_columns=["생산량", "계획량"])

    # 3) 제품 키로 장비 판단을 붙인다. 조인 결과가 1:1이어야 한다면 여기서 검증한다.
    rows = left_join_one_to_one(totals, equipment_assign, key="제품")

    # 4) 비율은 합산된 분자·분모로 다시 계산한다.
    result = []
    for row in rows:
        plan = row["계획량"]
        rate = round(row["생산량"] / plan * 100, 1) if plan else None
        if rate is not None and rate < 90:
            result.append({
                "제품": row["제품"],
                "생산실적달성율": rate,
                "장비교체판단": row["장비교체판단"],
                "필요장비대수": row["필요장비대수"],
            })
    return result

핵심: 조인 키·중복 처리·수량 합계·비율 재계산은 Recipe 안에 있습니다. 이 부분이 Report마다 달라지는 업무 코드입니다.

4. 00E Context Publisher는 정확히 무엇을 자동으로 할까?

00E는 Report의 업무 규칙을 대신 계산하지 않습니다. 대신 완성된 View를 후속 질문에 안전하게 쓰도록 “보관·공개·검증”합니다.

5. 예시 ② — 중간 소스가 10개여도 같은 방식이다

원천이 많아진다고 Flow 07-2가 복잡해지는 것은 아닙니다. 복잡함은 Recipe 안에 머물고, 후속 질문에는 작은 결과 View만 전달합니다.

공정 위험 종합 Report의 내부 재료

생산 + 계획 + 재공 + 장비 + UPH + 불량 + HOLD + CAPA + 작업자 + 일정

↓

Report Recipe가 각 소스의 기준일·조인 키·중복·집계 방식을 확인하고 다음 세 개의 결과를 만듭니다.

공개 Viewprocess_risk_summary

공정 위험 View — 공정, 위험 점수, 병목 원인, 가동률. 공정 단위로 정렬·필터·Top N.

기본 Viewproduct_risk_summary

제품 위험 View — 제품, 달성율, 재공, 장비 위험, HOLD 여부. 사용자가 가장 많이 묻는 대상이라 기본 View로 공개.

공개 Viewkpi_summary

KPI 요약 View — KPI 이름, 목표, 실적, 상태. 정렬·열 선택에 적합한 작은 표.

비공개 Evidencejoin_audit_detail

조인 검증용 Evidence — 개발·감사용입니다. followup_enabled를 켜지 않으면 Flow 07-2의 질문 대상이 되지 않습니다.

서로 다른 컬럼명도 괜찮습니다 Report A가 제품, 생산달성율, 부족수량을 쓰고, Report B가 LOT_ID, HOLD_CODE, HOLD_TIME을 쓰고, Report C가 공정, 장비기종, UPH, 가동률을 써도 됩니다. Flow 07-2는 전역 DEN, MODE, MCP_NO를 억지로 강제하지 않고, 저장된 해당 View의 실제 컬럼만 사용합니다.

그렇다면 원천 10개는 어디에 기록할까?

업무적으로 필요한 원천 목록·조인 규칙·실행 진단은 Recipe 내부 상수, Recipe의 trace, Report 설계 문서에 둡니다. Flow 07-2가 사용하는 Bundle에는 사용자에게 공개할 완성 View만 넣습니다. 현재 00E는 한 Bundle에서 최대 12개 View를 처리하도록 구성되어 있으므로, 공개 View는 그 안에 가볍게 유지하는 것이 좋습니다.

6. Flow 07-2는 어떤 후속 질문을 처리할까?

Flow 07-2는 “이미 만들어져 저장된 Report View를 더 잘 보는” 역할입니다. 새 계산이나 원천 조회를 맡기지 않습니다.

가능: View 내부 필터

“방금 Report에서 장비필요 제품만 보여줘”

동작

장비교체판단 = 장비필요 행만 선택합니다.

가능: 정렬 + 상위 N

“생산실적달성율이 낮은 순으로 5개 보여줘”

동작

실제 생산실적달성율 열을 숫자 정렬하고 상위 5행을 반환합니다.

가능: 컬럼 선택

“제품, 달성율, 필요장비대수만 보여줘”

동작

View에 존재하고 공개된 세 열만 보여 줍니다.

상위 Router가 Flow 01로 라우팅: 최신 데이터

“현재 WIP도 함께 알려줘”

이유

Snapshot에 없는 최신 외부 데이터가 필요합니다. Flow 07-2는 자동 조회로 전환하지 않으며, 직접 들어온 요청은 차단·안내합니다.

상위 Router가 Flow 01로 라우팅: 새 조인

“이 Report와 불량 데이터를 조인해서 비교해줘”

이유

새 데이터셋과의 결합은 다시 조회·검증해야 합니다. Flow 07-2는 새 조인을 실행하지 않고, 상위 Router가 일반 분석 Flow로 보냅니다.

왜 제한하는가? Report 시점의 결과에 “몰래 새 데이터가 섞이는 것”을 막기 위해서입니다. View에 없는 열, 새 조인, 원천 재조회는 상위 Router/호출 애플리케이션이 Flow 01로 라우팅해야 하며, Flow 07-2는 이를 스스로 실행하지 않습니다.

7. HTML Report도 중간 소스가 아니라 최종 View를 기준으로 만든다

HTML 화면도 Recipe와 같은 완성 View를 입력으로 사용하면 됩니다. 즉, “제품 위험 표”, “공정 위험 차트”, “KPI 카드”는 각각 대응하는 View를 그립니다.

화면과 View의 대응

HTML 영역사용하는 View
KPI 카드kpi_summary
제품 위험 표product_risk_summary
공정 위험 차트process_risk_summary
상세 목록case_detail_view

이 방식의 장점

HTML과 후속 질문이 같은 결과를 보므로, 화면에는 A를 보여 주고 후속 질문에는 B를 쓰는 불일치가 줄어듭니다.

원천 테이블 수가 늘어도 HTML Renderer의 입력은 “몇 개의 완성 View”로 안정적으로 유지됩니다.

def render_report_html(bundle):
    views = {view["view_key"]: view for view in bundle["views"]}
    kpis = views.get("kpi_summary", {}).get("rows", [])
    products = views.get("product_risk_summary", {}).get("rows", [])
    processes = views.get("process_risk_summary", {}).get("rows", [])

    return (
        render_kpi_cards(kpis)
        + render_table(products, columns=["제품", "생산실적달성율", "장비위험"])
        + render_process_chart(processes)
    )

이 함수는 View의 이름과 공개 컬럼만 알면 되므로, 조인 키나 원천 DB 구조를 다시 알 필요가 없습니다.

8. 새 Report를 만들 때 실제로 정의할 것

아래만 분명하면 새로운 Report 유형을 추가할 수 있습니다. 나머지 보관·후속 질문 인프라는 공용 00E와 Flow 07-2를 재사용합니다.

Recipe에서 반드시 정의

  • 필수 원천과 선택 원천
  • 조인 키와 1:1 / 1:N 관계
  • 중복 행을 처리하는 방식
  • 수량은 합계, UPH는 평균 등 집계 규칙
  • 비율을 평균하지 않고 재계산할지 여부
  • 공개할 최종 View와 컬럼
  • 필수 소스 실패·빈 데이터일 때의 메시지
  • 기본 후속 질문 대상 View 하나

00E / Flow 07-2가 공통 처리

  • 실제 행으로부터 컬럼 자동 추출
  • 안전한 내부 source alias 생성
  • 제한된 후속 질문 연산 계약
  • Result Store 저장에 필요한 Snapshot payload 생성
  • 같은 세션인지·만료됐는지 검증
  • 필터·정렬·상위 N·열 선택 실행
  • 외부 재조회·새 조인 차단 및 Flow 01 위임
  • 직전 “그중” View 계획 유지

가장 작은 작업 순서

  1. Report 질문을 하나 정한다.예: “공정별 장비 위험 현황을 보여줘”.
  2. 그 질문에 필요한 원천과 계산식을 Recipe에 작성한다.원천 3개든 10개든 이 단계에만 존재합니다.
  3. 사용자에게 보여 줄 결과를 1~3개 View로 만든다.각 View의 실제 행, 표시명, 공개 컬럼만 정합니다.
  4. Bundle을 00E에 연결한다.00E가 Snapshot/Result Store 저장용 payload와 후속 질문용 계약을 자동 생성합니다.
  5. HTML Renderer도 같은 View를 사용한다.화면과 후속 질문이 같은 결과를 보게 됩니다.
  6. 후속 질문을 검증한다.필터, 정렬+Top N, 컬럼 선택, 최신 데이터 전환, context 없는 질문을 각각 확인합니다.

9. 자주 생기는 오해와 피해야 할 구현

“중간 소스 10개를 View Bundle에 전부 넣으면 더 유연하지 않을까?”
아닙니다. 그렇게 하면 Flow 07-2가 어떤 조인·집계·기준일을 써야 하는지 다시 판단해야 합니다. 이는 일반 분석 Flow와 같은 복잡도를 다시 만들고, Report 당시 결과와 다른 답을 만들 위험도 커집니다. 최종 View만 공개해야 후속 질문의 범위가 작고 명확합니다.
“컬럼명이 표준 컬럼과 다르면 전역 매핑을 추가해야 할까?”
후속 질문 전용 View에는 꼭 그렇지 않습니다. 예를 들어 장비기종, 가동률, HOLD_TIME처럼 Report가 실제로 가진 열을 그대로 사용하면 됩니다. 전역 Catalog 매핑은 새 원천을 다시 조회하는 Flow 01에서 필요할 수 있지만, 저장된 View에서는 실제 컬럼이 권위입니다.
“View의 비율을 후속 질문에서 다시 집계해도 될까?”
현재 Flow 07-2의 역할은 filter/sort/top-N/select입니다. 비율 재집계처럼 분자·분모 규칙이 필요한 일은 Recipe에서 미리 제품 View나 공정 View로 만들어 두는 것이 안전합니다.
“Report마다 너무 많은 View가 필요하면?”
현재 00E는 Bundle의 최대 12개 View를 처리합니다. 사용자가 실제로 질문할 가능성이 높은 View만 공개하고, 개발·감사용 Evidence View는 비공개로 두세요. 12개를 안정적으로 넘겨야 한다면 evidence와 query View를 별도 계층으로 확장하는 설계를 먼저 검토합니다.

마지막 요약

새 Report를 만들 때 매번 다시 만들 필요가 있는 것 업무 계산 Python Recipe와 HTML 화면 구성입니다.
공통으로 재사용되는 것 실제 컬럼 추출, Snapshot/Result Store 저장용 payload 생성, 세션 검증, 제한된 후속 질문 계약, Flow 07-2의 filter/sort/top-N/select 실행입니다.

따라서 Report의 원천이 3개에서 10개로 늘어나도, 후속 질문 쪽의 구조와 안전성은 거의 변하지 않습니다. 복잡한 업무 규칙은 Recipe에 모으고, Flow 07-2에는 검증된 최종 결과만 넘기는 것이 이 구조의 핵심입니다.

기준 구현: Flow 07(기존 직접 Report), Flow 07-1(향상된 Report + Context Publisher), Flow 07-2(저장 View 후속 질문).
이 문서는 프로젝트 내부 학습용 안내서이며, 실제 연결 포트와 상세 입력명은 해당 Flow JSON 및 Component 설명을 기준으로 확인합니다.
