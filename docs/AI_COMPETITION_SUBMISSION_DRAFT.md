# 사내 AI 공모전 제출 초안

> 이 문서는 현재 저장소에서 확인할 수 있는 구현, 검증 근거를 바탕으로 작성한 5페이지 원고다.<br>
> 업무 처리시간, 월간 절감시간, 사용자 만족도처럼 아직 실측 근거가 없는 값은 임의로 만들지 않고 `[실측값]`으로 표시했다.

## 사례명

**현업의 일하는 방식을 그대로 검증 가능한 제조 데이터 분석으로**<br>
Metadata-Driven Manufacturing Data Agent

### 한 줄 요약

현업의 자연어 질문을 제조 Domain, Table Catalog, 실행 규칙에 연결해 조회, 분석, 검증, 설명을 이어 주는 제조 데이터 분석 Agent

> 제조 현업이 Excel로 반복하던 데이터 가공 업무를, 제조 Domain과 개발 역량의 협업으로 재사용 가능한 분석 Flow로 바꿨다.

# 1페이지. 사례 요약

## 제조 현업의 한 문장 질문을 실행 가능한 분석으로

P&T 공정은 고객 요구사항과 시장 변화에 따라 생산 상황을 빠르게 확인해야 합니다. 제품, 공정 구성, 관리 목적이 달라지면 같은 지표라도 기준일, 공정 범위, 제품 단위, 사용하는 데이터와 집계 방식이 달라집니다. 현업은 그때그때 질문과 조건을 정해 데이터를 다시 조합해야 합니다.

"오늘 DA공정 생산량 알려줘", "SBM공정 제품별 보유CAPA 알려줘" 같은 질문은 반복되지만, 답을 만드는 과정은 매번 달랐습니다. 담당자는 날짜와 공정, 제품 조건을 해석하고, 맞는 데이터와 컬럼을 찾은 뒤 필요하면 여러 원천을 결합해 계산해야 했습니다. 데이터마다 컬럼명과 기준이 달라 현업은 여러 시스템에서 데이터를 내려받아 Excel로 필터링, 집계, 비교를 반복했고, 숙련도에 따라 조건 누락, 잘못된 원천 선택, 재작업과 결과 편차가 생길 수 있었습니다.

이 Agent는 현업 질문을 Metadata 기반 실행 계약으로 바꿔 실제 데이터 조회와 분석으로 연결합니다.

Agent는 질문에서 지표, 날짜, 공정, 제품 조건을 파악합니다. 등록된 Domain과 Table Catalog를 바탕으로 데이터와 적용 조건, 반영해야 할 로직을 정합니다. AI는 질문의 의미와 분석 계획을 맡고, 실제 데이터 연결, 물리 컬럼, 필수 파라미터는 Metadata와 Python 코드 기반 실행기가 관리합니다. 전체 기능은 Agent Builder(Langflow) 기반의 시각적 Flow로 구성해 다른 공정이나 조직에서도 재사용할 수 있도록 구현했습니다.

현업의 경험으로 쌓인 암묵지와 일하는 방식은 Domain 지식, Table Catalog, 공통 Filter 기준으로 정리했습니다. AI가 반복 분석을 먼저 수행하고, 사용자는 근거를 검토한 뒤 최종 판단에 집중하도록 업무 흐름을 바꿨습니다.

예를 들어 "D/A공정 78LEAD 제품별 장비현황과 CAPA 알려줘"라는 질문은 등록된 CAPA 업무 규칙에 따라 다음과 같이 처리됩니다.

```text
자연어 질문
  → D/A 공정, 78LEAD, 장비현황, CAPA 의도 파악
  → 장비할당 데이터(equipment_assign)와 장비 UPH정보(eqp_uph) 선택
  → 공정, 장비모델, RECIPE 기준으로 결합 (JOIN기준 반영)
  → 장비 대수와 평균 UPH 집계
  → 장비 대수 × 평균 UPH × 24시간 계산 (CAPA로직 반영)
  → 제품별 CAPA 합산
  → 결과표와 분석 근거 Report 제공
```

현업 구성원은 정리된 결과와 데이터를 전달받고, 필요할 때 분석처리 과정을 담은 HTML Report에서 적용된 데이터와 조건, 중간 결과, 계산 과정, 오류 원인을 확인할 수 있습니다. 데이터 탐색과 반복 가공은 AI가 먼저 처리하고, 사용자는 결과와 근거를 확인해 판단할 수 있습니다.

### 문제와 해결 방식

| 문제 | 해결 | 현재 확인된 변화 |
| --- | --- | --- |
| 데이터와 업무 기준이 분산되어 숙련자에게 의존 | Domain 지식, Table Catalog, 공통 Filter로 지식을 구조화 | 개인의 암묵지를 재사용 가능한 공통 자산으로 전환 |
| 질문마다 데이터 다운로드와 Excel 가공을 반복 | 질문을 검증 가능한 실행 계약으로 변환해 자동 실행 | 자연어 질문부터 결과표, 근거 Report까지 하나의 흐름으로 연결 |
| 조건 누락과 담당자별 해석 편차 | 메타데이터와 결정론적 실행 규칙으로 기준 통제 | 동일한 메타데이터와 실행 계약을 적용하도록 설계 |
| 결과만으로는 오류 원인을 확인하기 어려움 | 분석 처리 과정을 근거를 담은 HTML로 제공 | 코드에 익숙하지 않은 비개발자도 적용 조건과 실패 원인을 확인 가능|
| 새 업무를 확산하거나 기능을 추가 시 개발 지원이 필요 | 변하는 업무 방식은 메타데이터로, 정해진 업무는 Workflow 기반으로 확장 | 다른 공정, 조직에서도 재사용 가능한 Agent 기반 확보 |

### 시각자료 예시

```text
[Before]
질문 → 시스템/문서 확인 → 데이터 다운로드 → Excel 가공, 비교 → 검증 → 결과 정리

[After]
질문 → AI 의도 분석 → Metadata 검증 → 자동 조회, 분석 → 결과 + 근거 Report → 사람의 판단
```

# 2페이지. 사례 상세

## 1. 업무 성격 기반 가변형 제조 데이터 분석과 고정된 Workflow 형태를 분리

질문마다 조건과 데이터 조합이 달라지는 질의는 가변형 제조 데이터 분석(Flexible Analysis)으로 처리합니다. 이에 필요한 암묵지는 메타데이터 등록 Flow를 통해 자연어 기반으로 입력하면 LLM이 해석할 수 있는 형식으로 자동 변환되어 저장되도록 구현하였습니다.
업무 규칙, 판정 절차, 보고서 형식이 정해진 반복 업무 유형은 고정된 Workflow로 분리하여 Sub Agent로 구현하였습니다. 이 구분으로 변하는 질문에도 유연하게 대응할 수 있고, 반복되는 업무는 정해진 기준과 산출물 형식을 반환할 수 있는 구조를 완성하였습니다.

### 1-1. 고정된 Workflow를 Sub Agent로 호출

고정된 방식의 Workflow의 경우 업무의 규칙, 판정식, 보고서 형식 등은 독립된 Workflow로 만들고, Main Router Agent가 요청 성격에 맞을 때만 Sub Agent Tool로 호출합니다. 가변 데이터 분석과 고정 Workflow를 별도의 Tool로 선택하여, 고정 Workflow의 기준과 산출물이 가변형 분석 경로에 섞이지 않도록 구현했습니다.

새로운 고정 Workflow 업무는 독립 Workflow를 구성하고 Tool 연결을 추가하는 방식으로 확장합니다. 업무별 Rule과 Report 형식은 고정 Workflow가 관리하고, Router는 질문을 적합한 실행 경로로 연결합니다. 현재는 실시간 생산 분석 업무가 구현되어 있으며, 제조 현업에서 추가로 발굴한 45개 후보 업무도 우선순위에 따라 단계적으로 개발하고 있습니다.

### 1-2. 자연어 기반 메타데이터 등록과 메타데이터 QA Flow

가변형 제조 데이터 분석의 기준은 현업이 이해하는 언어로 계속 추가하고 보완할 수 있어야 합니다. Domain지식, Table Catalog, Main Filter기준의 메타데이터 등록 Flow를 구성하여, 코딩 역량이 상대적으로 부족한 제조 현업에서도 운영 가능한 환경을 구성하였습니다. 작업자가 입력한 자연어를 등록 후보로 바꾸고, 기존 항목과의 중복 및 유사성, 필수 계약을 확인한 뒤 저장합니다.

메타데이터 QA Flow에서는 등록된 공정, 지표, 데이터셋, 필터 기준 등을 자연어로 확인하고 비교할 수 있습니다. 현업 작업자는 새 기준을 등록하고 검토하며, 개발자는 신규 기능이 필요할 때마다 코드를 수정하지 않아도 됩니다.

## 2. 가변형 제조 데이터 분석을 위한 공통 실행 구조

### 2-1. 현업 지식의 메타데이터 구조화를 통한 분석 처리

Metadata는 세 영역으로 나눴습니다. Domain에는 공정 그룹, 지표 의미, 제품 해석, 계산식과 업무 규칙을 담습니다. Table Catalog에는 데이터셋, 실제 컬럼, 조회 파라미터, 필터 매핑과 사용 시점을 담습니다. Main Filter 기준에는 여러 질문에 공통으로 적용할 필터 기준을 둡니다.
가변형 제조 Data 조회 Flow는 이 메타데이터를 기반으로 실행 계획을 세우고 분석을 진행합니다.
### 2-2. AI의 질문 해석과 데이터 실행 역할 구분

```text
AI가 결정하는 것
  지표 의미, 날짜 의미, 공정/제품 조건, 분석 의도, 결과 설명

메타데이터와 Python 코드 기반 실행기가 처리하는 것
  실제 데이터 연결, 물리 컬럼, 필수 파라미터, 조인/계산 계약, 실행 검증
```

이 구분으로 AI는 언어 해석에 집중하고, 실행기는 등록되지 않은 테이블이나 컬럼을 임의로 사용하지 않도록 막습니다.

### 2-3. 실행 가능한 분석 계획 수립

LLM이 만든 분석 계획은 바로 실행하지 않습니다. 계획 정규화기가 LLM 응답을 표준 실행 계획으로 정리하고, 데이터 조회 작업, 데이터 source, 단계 연결, 컬럼 소유권, 필수 조회 파라미터, 필터, 결과 계약을 확인합니다. Metadata와 정해진 규칙으로 확정할 수 있는 누락은 보완하고, 근거가 부족한 항목만 확인이 필요하다고 안내합니다.

초기 검증에서는 필터 누락, 숫자와 문자 형식 불일치, 중간 계산값의 원본 컬럼 오인, 조인 단위 오류, 후속 질문 조건의 잘못된 상속 때문에 정상 질문도 0건 또는 실패가 발생했습니다. 정규화와 계약 검증을 거쳐 설명은 그럴듯하지만 실행되지 않는 계획을 줄이고, 실행 가능한 요청은 끝까지 처리하도록 했습니다.

### 2-4. 분석 난이도에 따른 Fast와 Complex 경로 분기

사내 LLM 호출 부하가 큰 환경에서는 단순 질문까지 LLM 기반 코드 생성으로 처리하면 응답 시간이 길어집니다. 현업이 자주 사용하는 단일 데이터 조회, 합계, 개수, 정렬, 상하위 분석, 단순 그룹 집계는 LLM 호출 없이 Fast 분기에서 사전에 정의한 결정론적 로직으로 처리합니다.

조인, 비교, 파생 계산처럼 해석과 단계 구성이 필요한 복합 요청은 Complex 분석 경로로 보냅니다. LLM은 필요한 pandas 처리 코드 생성에 사용하고, 오류 발생 시 Repair는 최대 한 번만 시도합니다. 이 방식으로 응답 시간과 모델 부하를 줄이면서 분석의 완성도를 높였습니다.

### 2-5. 분석 문맥 기반 멀티턴 응답 기능 구현

멀티턴 응답을 위하여 저장소(MongoDB)에 `session_id` 기준으로 이전 질문과 답변, 선택한 분석 경로, 원본 및 결과 데이터의 저장 참조를 기록합니다. 후속 질문이 들어오면 문맥에 따라 LLM이 후속 분석인지를 판단하여 처리하도록 구현하였습니다.

- 원본 데이터의 조회에 사용하는 필수 파라미터 자체를 변경하는 경우 신규 조회
- 이전 원본에서 다시 적용할 수 있는 단순 필터 조건은 기존 결과를 재사용
- 재사용 가능 여부가 애매한 경우 잘못된 이전 데이터를 사용하지 않고 신규 조회

### 2-6. HTML Report 기반 분석 근거 제공

비개발자도 결과를 검토하고 이상한 점을 개발자에게 정확히 전달할 수 있도록, 결과표와 별도로 HTML 분석 Report를 만들었습니다. 사용자는 분석이 어떤 데이터와 조건을 거쳐 생성됐는지 한 화면에서 확인할 수 있습니다.

- 질의 의도 해석, 사용한 메타데이터 정보, 적용 필터와 로직, 실행 경로를 단계별로 표시합니다.
- 원본, 중간 처리 결과, 최종 데이터를 확인 가능하도록 구현하였고 CSV 다운로드를 지원합니다.
- 분석 과정 도중에 오류가 나는 경우도 실패한 단계와 원인 분석이 가능하도록 구현하였습니다.

### 2-7. 검증 질문셋 기반 품질 관리

가변형 제조 데이터에서 실제 사용자들이 주로 사용하는 질문 패턴을 정리하여 검증 질문 세트를 구성했습니다. 모델을 바꾸거나 Flow 구조를 수정한 뒤에는 이 품질 기준 질문셋을 기반으로 기존 사용 가능했던 범위에 문제가 없는지를 확인하는 Process를 구성하였습니다.

## 3. 추진 기간과 속도

초기 구현 이후 수십 차례에 걸쳐 질문을 실행하고, 결과를 검증하고, Flow를 수정했습니다. 실제 질문에서 발견된 실패는 대표 질문과 회귀 테스트로 남겼습니다. 필터, 조인, 시간, 컬럼 소유권 문제는 질문별 예외가 아니라 공통 실행 문제로 정리해 보완했습니다. 분석, Metadata 저장, 결과 저장, HTML Report, Router, 멀티턴, 채널/API 연계는 역할별 Flow로 나눠 재사용할 수 있게 했습니다.

### 3-1. 개발 여정

```text
1단계  질문을 실행 가능한 Metadata/계약으로 구조화
   ↓
2단계  Fast/Complex 분석과 데이터 조회, 결과 저장 연결
   ↓
3단계  대표 검증 질문셋으로 필터, 조인, grain, 검증 계약 점검
   ↓
4단계  HTML 설명 Report와 원본, 중간, 최종 데이터 공개
   ↓
5단계  Router, 멀티턴, 결과 전달 경계를 연결해 사용성 확장
```

## 4. 횡전개를 고려한 구조로 전사 확산 가능성

지금 Agent Builder기반으로 구현된 구조는 특정 공정이나 업무 영역에 종속되지 않습니다. 질문 형태가 계속 달라지는 업무는 메타데이터 기반 가변형 제조 데이터 분석으로, 판정 절차와 산출물이 정해진 반복 업무는 고정 Workflow Report로 확장할 수 있습니다. 검증된 Langflow Flow를 공통 Template처럼 재사용하고, 적용하고 싶은 조직은 자신들의 메타데이터만 등록한다면 즉각적인 기능 확장이 가능한 구조로 구현하였습니다.

## 3. 정성적 성과: 개인의 분석 경험을 검증 가능한 업무 자산으로 전환

이번 사례의 현재 성과는 자연어 질의가 가능한 화면을 만든 데 있지 않습니다. 제조 현업이 각자 경험으로 보유하던 데이터 선택 기준, 날짜 해석, 공정과 제품 조건, 계산식과 예외 판단을 Domain, Catalog, Filter, Workflow로 구조화해 반복 실행 가능한 자산으로 전환한 데 있습니다.

### 3-1. 숙련자 의존 분석 기준의 공동 자산화

기존에는 어떤 데이터를 선택하고 어떤 조건을 적용할지 담당자의 경험과 Excel 작업 방식에 크게 의존했습니다. Agent는 생산량, 재공, LOT, 장비, UPH, CAPA처럼 서로 다른 지표의 원천과 계산 기준을 Metadata로 관리합니다. 동일한 질문은 개인의 기억이 아니라 등록된 업무 기준을 바탕으로 처리되므로, 분석 기준을 공유하고 지속적으로 보완할 수 있는 기반을 만들었습니다.

### 3-2. 결과 숫자 중심 업무에서 근거 확인 중심 업무로 전환

사용자는 결과표만 받는 것이 아니라 HTML 분석 Report에서 적용된 Domain, 조회 데이터, 필수 파라미터, 필터, 중간 데이터, 집계와 조인 과정, 오류 원인을 확인할 수 있습니다. 비개발자도 결과가 만들어진 경로를 확인하고 이상 징후를 구체적으로 전달할 수 있어, AI 결과를 맹목적으로 수용하는 방식이 아니라 사람이 근거를 검토하고 최종 판단하는 업무 흐름을 구현했습니다.

### 3-3. 수정 경험을 반복 품질 자산으로 축적

실제 질문에서 발견된 필터 누락, 숫자와 문자 형식 차이, 날짜 해석, 조인 단위, 중간 계산 컬럼 오류는 개별 질문만 통과시키는 예외 코드로 처리하지 않았습니다. 대표 질문, 멀티턴, 날짜 계약 시나리오와 자동 회귀 검증 기준으로 축적했습니다. 따라서 모델이나 Flow 구조를 변경할 때도 기존에 가능했던 분석 범위가 훼손되지 않는지 반복 확인할 수 있습니다.

### 3-4. 현업 확장 방식의 전환

새로운 분석 요구는 범용 Agent의 Prompt를 계속 늘리는 대신 Metadata를 등록하거나, 업무 기준과 보고서 형식이 고정된 경우 독립 Workflow를 Sub Agent Tool로 연결하는 방식으로 확장합니다. 현업의 Domain 지식은 현업이 관리하고, 개발 구조와 실행 계약은 재사용함으로써 새 공정과 지표에 대한 적용 부담을 낮췄습니다.

## 4. 제출 전 확보할 현업 KPI

현재 저장소에는 기존 수작업 시간, 월 처리건수, 현업 오류율, 만족도에 대한 실측 데이터가 없습니다. 아래 지표를 확보하면 공모전 성과를 실제 값으로 제시할 수 있습니다.

| KPI | 측정식 | 제출 문구 예시 |
| --- | --- | --- |
| 평균 분석 리드타임 | 수작업 중앙값 vs Agent 실행+검토 중앙값 | `[기존 N분] → [N분], [N%] 단축` |
| 월간 절감시간 | 월간 분석 건수 × 건당 절감시간 | `월 [N시간] 절감` |
| 1차 검수 통과율 | 수정 없이 승인된 건수 ÷ 전체 검증 건수 | `대표 질문 [N건] 중 [N건], [N%]` |
| 재작업률 | 조건 누락, 잘못된 원천 선택으로 재실행한 건수 ÷ 전체 | `[N%] → [N%]` |
| Metadata 확장시간 | 신규 분석의 코드 개발시간 vs Metadata 등록, 검증시간 | `[N일] → [N시간]` |

### 실측 방법

1. 자주 쓰는 대표 업무 10건을 선정한다.
2. 기존 방식과 Agent 방식으로 각각 3회 수행해 총 30쌍의 시간을 기록한다.
3. 시작, 종료 시각, 1차 통과 여부, 재작업 횟수, 오류 유형, Report 발행 여부를 함께 남긴다.
4. 평균보다 이상치 영향을 덜 받는 중앙값을 대표값으로 사용한다.
5. 현업 사용자 3~5명에게 이해도, 신뢰도, 재사용 의향을 5점 척도로 확인한다.

### 실측 후 사용할 문장

> 대표 제조 데이터 업무를 대상으로 비교한 결과, 기존에는 데이터 확인과 조건 적용, 집계 및 결과 정리에 건당 중앙값 `[N분]`이 소요됐으나 Agent 적용 후 결과 검토를 포함해 `[N분]`으로 단축되어 처리시간이 `[N%]` 감소했습니다. 1차 검수 통과율은 `[N%]`, 재작업률은 `[N%]`를 기록했으며, 월간 반복 질의 `[N건]` 기준 `[N시간]`을 절감할 수 있었습니다.

# 4페이지. SKMS / SKMS CoC 소구 포인트

## 실행되는 답변과 검증 가능한 근거를 함께 만든 AI Agent

본 사례는 자연어로 답변을 생성하는 챗봇을 구현한 사례가 아닙니다. 제조 현업의 가변적인 질문을 실제 데이터 조회, 분석 실행, 근거 확인까지 연결하고, 실패 경험도 다음 품질 개선의 자산으로 축적하는 업무 구조를 만든 사례입니다. 제조 구성원이 아닌 수행자가 현업의 Domain 지식과 개발 역량을 결합해, 개인의 경험에 머물던 업무 기준을 재사용 가능한 Flow와 Metadata로 전환했다는 점에 의미가 있습니다.

## 소구 1. SUPEX와 패기: 답변을 넘어 실행 가능한 분석으로

제조 데이터 분석에서는 질문 의도를 잘 설명하는 것만으로 충분하지 않습니다. 실제로는 필터가 누락되거나 숫자와 문자 형식이 달라 결과가 0건이 되거나, 조인과 집계 단위가 맞지 않아 결과가 왜곡될 수 있습니다.

이 Agent는 LLM이 만든 계획을 그대로 실행하지 않고 정규화와 실행 계약 검증을 거쳐 데이터 조회 조건, 컬럼 소유권, 단계 연결, 결과 계약을 확인합니다. 수십 차례의 질문, 실행, 검증, 수정 과정을 통해 “답변이 가능한가”가 아니라 “현업이 실제로 사용할 수 있는 결과인가”를 기준으로 완성도를 높였습니다. 이는 어려운 문제를 회피하기보다 실행 가능한 구조로 끝까지 풀어낸 SUPEX와 패기의 실천입니다.

## 소구 2. Commitment와 솔선수범: 사용자 확인의 마지막 단계까지 책임

현업의 불편은 결과를 얻기 전의 데이터 탐색과 Excel 가공에만 있지 않았습니다. 결과가 이상할 때 어떤 데이터와 조건이 적용됐는지 알기 어려워 다시 담당자를 찾아가야 하는 문제도 있었습니다.

이를 해결하기 위해 자연어 Metadata 등록, 가변형 데이터 분석, Fixed Workflow Sub Agent, Router, 결과 저장, HTML 분석 Report를 연결했습니다. 분석이 정상 완료된 경우에는 결과의 근거를, 오류가 발생한 경우에는 실패 단계와 가능한 중간 결과를 보여 줍니다. 단순히 결과를 반환하는 데서 멈추지 않고 사용자가 확인하고 보완할 수 있는 마지막 단계까지 책임지는 구조를 구현했다는 점에서 Commitment와 솔선수범의 의미가 있습니다.

## 소구 3. Teamwork 및 안정과 성장: 제조 암묵지와 개발 역량의 결합

제조 현업은 공정, 제품, 지표, 계산 기준, 실제 실패 사례를 제공하고 검토했습니다. 수행자는 이를 Langflow 기반 Flow, Metadata 계약, 실행 규칙, 검증 질문셋, HTML Report 구조로 구현했습니다. 제조 지식만으로는 재사용 가능한 시스템을 만들기 어렵고, 개발 역량만으로는 현업 기준에 맞는 분석을 만들기 어렵습니다.

두 역할이 결합되면서 현업의 암묵지는 Domain과 Workflow로 남고, 개발 구조는 다른 공정과 반복 업무에 재사용할 수 있게 됐습니다. 현재 실시간 생산 분석 Fixed Workflow를 우선 구현했으며, 발굴된 반복 업무 후보에도 우선순위에 따라 같은 방식의 적용을 준비할 수 있는 기반을 확보했습니다. 이는 단발성 자동화가 아니라 안정적으로 성장할 수 있는 협업형 AI 운영 모델이라는 점에서 의미가 있습니다.

### 페이지 마무리 문장

> 현업의 암묵지를 실행 가능한 기준으로 바꾸고, AI의 분석 결과를 사람이 검증할 수 있게 만든 것이 본 사례의 핵심 성과입니다.

```text
업무 질문 접수
  → 담당자가 사용할 시스템과 테이블 탐색
  → 날짜, 공정, 제품 조건 해석
  → 여러 시스템에서 데이터 다운로드
  → Excel로 필터, 중복 제거, 집계, 비교
  → 업무 계산식 적용
  → 결과 이상 여부 역추적
  → 표와 설명 작성
  → 후속 질문이 오면 다시 조건과 데이터를 복원
```

- 여러 시스템과 문서를 반복 확인
- 데이터 구조와 계산 기준을 아는 숙련자에게 의존
- 같은 질문도 담당자별 조건 해석에 따라 결과가 달라질 가능성
- 질문이 바뀔 때마다 데이터 다운로드와 Excel 가공을 반복
- 조건 누락과 계산 오류를 최종 결과에서 뒤늦게 발견
- 후속 질문 시 이전 데이터와 조건을 다시 설명하거나 재구성
- 결과만 전달되어 비개발자가 오류 원인을 확인하기 어려움

## AI 적용 후 프로세스

```text
현업 자연어 질문
  → Router가 가변형 제조 데이터 분석 또는 Fixed Workflow Sub Agent Tool 선택
  → AI가 지표, 날짜, 공정, 제품 조건 해석
  → Metadata가 데이터, 컬럼, 필수 조건 검증
  → Fast 또는 Complex 경로로 자동 실행
  → 결과표와 자연어 답변 생성
  → HTML Report로 처리 근거와 데이터를 제공
  → 후속 질문은 조건 변화에 맞춰 재사용 또는 재조회
```

## AI로 바뀐 지점

| 변화 영역 | Agent의 역할 | O/I 효과 |
| --- | --- | --- |
| 업무 분류 | Router가 가변형 제조 데이터 분석 또는 Fixed Workflow Sub Agent Tool 선택 | 잘못된 처리 경로 감소 |
| 의미 해석 | 생산량, 재공, LOT, UPH, CAPA와 날짜, 공정, 제품 조건 구조화 | 담당자별 해석 편차 감소 |
| 데이터 선택 | 시점, 지표에 맞는 등록 Catalog 선택 | 반복 탐색과 잘못된 원천 선택 감소 |
| 분석 실행 | 필터, 중복 제거, 집계, 정렬, 조인, 파생 계산 자동화 | 수작업과 리드타임 감소 |
| 실행 검증 | 필수 파라미터, 컬럼 소유권, 조인 grain과 결과 계약 확인 | 누락, 왜곡, 재작업 위험 감소 |

| 후속 대응 | "WB공정은?", "어제는?", "세부 제품별로"를 문맥과 연결 | 반복 설명과 재분석 부담 감소 |
| 업무 확장 | 자연어 Metadata 또는 재사용 가능한 Langflow Workflow로 신규 기능 추가 | 개발 의존도와 확장 리드타임 감소 |

## Operation Improvement 효과

```text
Before  사람이 데이터 탐색부터 결과 작성까지 전 과정을 직접 수행
After   AI가 반복 조회, 분석, 설명을 선행하고 사람이 근거 검토와 최종 판단에 집중
```

질문 접수, 업무 의미 해석, 데이터 선택, 분석 실행, 결과 검증, 설명과 후속 대응을 하나의 재사용 가능한 운영 흐름으로 연결했습니다.

### 실측할 효과

- 분석 처리시간 단축
- 반복 조회, 정리 업무 감소
- 담당자별 분석 편차와 숙련자 의존도 감소
- 조건 누락과 재작업 감소
- 분석 기준의 표준화
- 결과 추적성과 설명 가능성 향상
- 신규 데이터와 유사 업무로의 확장 속도 향상

### 마무리 문장

> 현업의 질문, 업무 지식, 데이터 구조, 계산 기준을 연결하는 공통 실행 체계를 만들고, 사람이 반복하던 데이터 탐색과 분석을 AI가 먼저 처리하도록 업무 흐름을 바꿨습니다.

## 제출 전 확인할 사항

- `[실측값]`을 실제 현업 비교 결과로 교체한다.
- 현재 기본 조회 모드는 dummy이므로 live 운영 적용 범위를 실제 상태에 맞게 표현한다.
- "정확도 100%", "전사 적용 완료"처럼 근거 없는 표현은 사용하지 않는다.
- 자동 회귀 테스트의 단일 통과 건수는 제출 직전에 최신 실행 로그를 확보한 뒤 기재한다. 현업 데이터 정확도 수치와 혼용하지 않는다.
- 전체 테스트를 모두 통과했다고 표현하지 않는다. 별도 문서/소스 동기화 감사 항목은 제출 전 정리한다.
- Report 후속 분석 Flow는 현재 운영 Router에 노출되지 않으므로 일반 멀티턴과 구분한다.
- 사내 정보보안 기준에 따라 화면의 데이터, 서버 주소, 사용자 ID와 다운로드 링크를 마스킹한다.
